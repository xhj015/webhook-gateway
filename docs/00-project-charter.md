## 二、项目背景与动机

1. **学习动机**：想系统学习 Go，尤其是并发与后端工程化，需要一个"能逼自己用上 goroutine / channel / context"的真实项目。
2. **现实痛点**：系统间事件通知很常见，但直接 HTTP 调用不可靠（丢事件、无记录、无重试），自己实现一套可靠投递又重复劳动。
3. **约束条件**：
   - 只有 CPU 电脑，不能依赖大模型 / GPU
   - 不想做前端
   - 时间有限（17 周），必须严格控制范围

Webhook Gateway 恰好落在三者交集上：纯后端、技术密度高、范围可收敛。

---

## 三、项目目标

### 产品目标

> 把"不可靠的一次 HTTP 请求"，变成"有记录、可追踪、可重试的一次事件投递"。

### 学习目标（更重要）

| 能力 | 通过什么练到 |
|---|---|
| Go 语言基础 | 全项目 |
| 并发编程 | Worker 池、channel 队列、原子抢占 |
| HTTP 服务 | 接收 Webhook、REST API |
| 数据库工程 | SQLite 持久化、索引、状态机落库 |
| 可靠性设计 | 重试、退避、崩溃恢复、至少一次投递 |
| 工程化习惯 | 设计先行、测试、结构化日志、Docker、优雅退出 |

### 成功标准（项目结束时）

- [ ] 能稳定接收 Webhook 并返回 202，事件 100% 落库不丢
- [ ] 目标服务宕机时，事件自动重试，恢复后成功送达
- [ ] 重试耗尽的事件可一键手动重试
- [ ] 每次投递都有完整的 Attempt 审计记录
- [ ] 进程崩溃重启后不丢事件、不卡死事件
- [ ] 有一条 Docker 命令能跑起来，有一套单元测试能通过
- [ ] 能对着文档向别人讲清楚每一处设计取舍

## 四、范围管理

### V0.1 做

创建 Endpoint、接收 Webhook、落库、异步投递、自动重试、手动重试、事件与投递历史查询、SQLite 存储、CLI + REST API、基础测试。

### V0.1 不做

用户注册登录、权限系统、前端页面、消息队列中间件（Kafka/RabbitMQ）、分布式部署、签名验证、多租户、复杂监控告警。

### 版本路线

| 版本 | 主题 | 内容 |
|---|---|---|
| V0.1 | 核心闭环 | 接收 → 落库 → 异步投递 → 重试 → 查询 |
| V0.2 | 可靠性增强 | 签名验证、指数退避、错误分类细化 |
| V0.3 | 工程化 | Docker、配置管理、结构化日志、优雅退出、完整测试、性能基准 |
| V0.4+ | 平台化（可选） | 多用户、权限、管理界面、可观测性、告警 |

**纪律**：V0.1 期间任何"顺手加了也行"的功能一律记入 backlog，不顺手加。

## 五、里程碑计划（17 周）

| 阶段 | 周次 | 里程碑 | 交付物 |
|---|---|---|---|
| M0 设计先行 | 第 1~2 周 | 五份设计文档定稿 | docs/01~05 全部完成并自查 |
| M1 Go 起步 | 第 3~4 周 | 能写基础 HTTP 服务 | 一个能收 POST 并落库 SQLite 的最小程序 |
| M2 接收链路 | 第 5~6 周 | F2 接收流程跑通 | 返回 202、事件落库、边界校验（404/410/413） |
| M3 投递链路 | 第 7~9 周 | F3 异步投递跑通 | channel 队列 + Worker 池 + Attempt 记录 |
| M4 重试机制 | 第 10~11 周 | F4 自动重试跑通 | 递增间隔重试、次数上限、失败终态 |
| M5 查询与手动重试 | 第 12~13 周 | F5/F6 跑通 | Event 列表/详情/Attempt 历史 API、手动重试 |
| M6 健壮性 | 第 14 周 | 崩溃恢复可用 | processing 超时回收、重启不丢事件 |
| M7 测试 | 第 15~16 周 | 测试覆盖核心链路 | 接收/投递/重试的状态机测试通过 |
| M8 收尾 | 第 17 周 | 可交付 | Dockerfile、README、项目复盘 |

每阶段完成标准：**在真实终端里演示对应流程走通**，而不是"代码写完了应该没问题"。

## 六、技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Go | 项目首要学习目标 |
| HTTP | 标准库 `net/http` + `chi` | 路由轻量，贴近标准库 |
| 数据库 | SQLite（`modernc.org/sqlite`） | 纯 Go 无 CGO，单文件零部署 |
| 队列 | 内存 channel + 数据库轮询兜底 | 不引入中间件，亲手实现队列语义 |
| CLI | `cobra` | Go 生态事实标准 |
| 配置 | 环境变量 + `viper` | 简单场景够用 |
| 日志 | `log/slog` | 标准库自带，结构化 |
| 测试 | `testing` + `httptest` | 标准库即可覆盖 |
| 部署 | Docker + 单二进制 | 交付形态简单 |

## 八、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围膨胀，想加多用户/前端 | 17 周完不成 | 铁律：只做 V0.1 清单内的事，新想法进 backlog |
| Go 并发写法踩坑（goroutine 泄漏、竞态） | 卡壳耗时 | 遇到问题回到小例子验证；用 `go vet` / `-race` 检查 |
| 至少一次投递带来重复投递困惑 | 误以为是 bug | 文档已明确语义；设计上让目标方幂等 |
| SQLite 并发写瓶颈 | 性能担忧 | V0.1 目标是正确性不是高并发，单 Worker 顺序写足够 |
| 时间不足，进度落后 | 里程碑顺延 | 优先砍 M7 测试规模，保 M2~M5 主链路；绝不砍设计文档 |
| 学了一堆技术但讲不出为什么 | 项目变技术堆砌 | 每个知识点对照 02-flow 的学习点映射表复盘 |

## 一、一句话与三个概念

> **把"不可靠的一次 HTTP 请求"，变成"有记录、可追踪、可重试的一次事件投递"。**

系统里只有三个概念，正好对应三张表：

| 概念 | 表 | 是什么 | 生命周期 |
|---|---|---|---|
| **Endpoint** 端点 | `endpoints` | 一个投递目标（一条 URL），回答"事件该往哪送" | 长期存在，可停用，不被删除 |
| **Event** 事件 | `events` | 一次待投递的 payload，系统为它的最终结果负责 | 有状态、会流转、有终态 |
| **Attempt** 投递尝试 | `attempts` | 一次真实的 HTTP POST 及其结果 | 只追加，写入后不再修改 |

对应关系：**一个 Endpoint 下有很多 Event，一个 Event 下有很多 Attempt。**

理解三张表的钥匙是这句话：**Event 是业务对象，Attempt 是审计记录。** Event 会变（状态流转），Attempt 不会变（一次投递发生了就是发生了，成功失败都记录下来）。

**"一次投递"的准确定义**：worker 把某条 Event 的 payload POST 到它的 Endpoint URL，并在 10 秒内拿到回应——无论结果如何，这一轮就是一次 Attempt。

## 二、业务规则（V0.1）

### 接收侧

| 编号 | 规则 | 不满足时 |
|---|---|---|
| B1 | 事件通过 `POST /hooks/{endpoint_id}` 进入系统 | 端点不存在 → 404 |
| B2 | 端点已停用则拒收新事件 | → 410 |
| B3 | payload 上限 1 MB | → 413 |
| B4 | **收到即落库，先写库再回 202**，不等投递结果 | 写库失败 → 500，绝不能返回 202 |
| B5 | 202 的响应体里必须带 `event_id`，供调用方对账 | — |

### 投递侧

| 编号 | 规则 | 说明 |
|---|---|---|
| B6 | 成功判定：**HTTP 2xx**，且在 10 秒内响应 | 3xx 也算失败（不跟随重定向，避免被引到意料之外的地方） |
| B7 | 每次投递都要写一条 Attempt（状态码、耗时、错误信息） | 失败原因必须可查，否则"能查"这条验收勾不上 |
| B8 | 失败后按 `5s → 30s → 2min → 10min → 1h` 递增间隔重试 | 最多 5 次，用尽即终态 `failed` |
| B9 | 投递时透传原始 payload，并附加 `X-Webhook-Event-Id` / `X-Webhook-Attempt` 头 | 前者给接收方做幂等去重，后者给排查用 |
| B10 | **端点停用只影响新事件**，在途事件继续投递完 | 停用是"别再送新的来"，不是"把在途的扔掉" |

### 人工侧

| 编号 | 规则 | 说明 |
|---|---|---|
| B11 | 手动重试只对 `failed` 开放 | 对 `delivered` 返回 409，避免误操作重投成功事件 |
| B12 | 手动重试 = **重置一次完整的重试预算**（次数清零、立即投递） | 人工介入的语义是"重新开始一轮"，不是"再给一次机会" |
| B13 | 手动重试**不删除历史 Attempt** | 审计链连续：第 6 次物理投递就是第 6 条记录 |

## 三、投递语义：至少一次

本项目采用 **at-least-once（至少一次）**：**保证不丢，不保证不重复。**

这不是缺陷，是明确的选择。原因来自一个无法回避的窗口：

```
worker 发出 POST ──► 目标服务已处理并返回 200 ──► 响应在网络上丢失
                                                └─ 网关不知道成功了

或者：worker 发出 POST ──► 目标服务已处理 ──► [进程被 kill]
                                                └─ 库里还停在 processing
```

这两种情况下，"目标到底收没收到"**在网关这一侧不可判定**。任何试图猜答案的做法都会在另一种情况下出错。所以只有一个安全方向：**当作没完成，再投一次。**

代价由接收方承担，且成本很低：

- 网关在投递时带上 `X-Webhook-Event-Id`，**同一个事件 ID 重复出现就是重复投递**；
- 接收方拿这个 ID 做一次去重判断即可（存一张已处理 ID 表，或把 ID 设成业务主键）。

**反过来说**：如果网关为了"不重复"而在不确定时放弃投递，那就是丢事件——这违背了项目的第一目标。**宁可重，不可丢。**

## 四、关键参数（V0.1 定死，不再浮动）

| 参数 | 取值 | 依据 |
|---|---|---|
| 单次投递超时 | 10 秒 | 参考 Svix 的 15 秒，取更保守的值 |
| 成功判定 | HTTP 2xx | 沿用 Svix 的"仅 2xx 算成功" |
| 重试次数上限 | 5 次 | Svix 为 8 次（总跨度约 42 小时），本项目压缩 |
| 重试间隔 | 5s → 30s → 2min → 10min → 1h | 参考 Svix 递增策略简化。总跨度约 1 小时 12 分 |
| payload 上限 | 1 MB | 超过返回 413 |
| processing 租约 | 60 秒 | 必须 **> 投递超时 10s**，否则会回收一个还在投的任务 |
| worker 数量 | 默认 1，代码按可配置 N 写 | SQLite 是单写者，V0.1 并发 1 最稳 |

## 五、业务边界（V0.1 不做）

| 不做 | 原因 |
|---|---|
| 端点删除 | 删了它的事件怎么办没想清楚，V0.1 只提供停用。删除进 backlog |
| 事件内容重放/编辑 | 网关是透明管道，不允许改 payload |
| 签名验证（HMAC） | 推迟到 V0.2，接收侧边界已预留 |
| 多租户、权限 | 单实例单用户，不引入 `tenant_id` |
| 消息队列中间件 | 亲手实现队列语义是学习目标，引入中间件等于把要练的东西外包 |
| 前端页面 | 全部通过 REST API + `curl` 操作 |
| 过滤/分页的高级形态 | V0.1 只做按状态过滤，分页可砍 |

**纪律条款**：任何"顺手加了也行"的东西进 `docs/03-scope.md` 的 backlog，V0.1 期间不顺手加。

## 六、这套业务逻辑靠什么立住

| 验收要求（项目书第九节） | 由哪条业务规则支撑 |
|---|---|
| 事件 100% 落库不丢 | B4（先写库再回 202）+ 数据库即唯一真相来源 |
| 目标宕机后恢复送达 | B8（递增退避，总跨度约 1 小时 12 分） |
| 重试耗尽可一键重试 | B11 + B12 + B13 |
| 每次投递都有完整审计 | B7（Attempt 不可变）+ B9（透传 event_id） |
| 崩溃重启不丢不卡 | 租约 60s + 回收规则（见 `02-flow.md` 第 4 节） |

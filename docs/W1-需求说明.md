# Webhook Gateway —— 需求汇报

> 用途：课程需求汇报。按课程给的八个要点组织，逐条对应。
> 详细业务逻辑与数据模型后续写进 `docs/01-business.md`、`docs/04-data-model.md`。

---

## 一、项目动机

**来源：个人兴趣加自身痛点。**

我想系统学习 Go，特别是并发编程和后端工程化。跟着教程写增删改查练不到这些，需要一个会主动制造并发、状态机和可靠性问题的真实项目。

同时我在实际接触中反复遇到一个麻烦：系统之间靠 HTTP 互相通知事件很常见（支付成功后通知订单系统、代码提交后通知 CI），但直连调用有三个问题：

1. 网络抖一下就丢事件，没有记录，事后查不到。
2. 下游服务重启期间发出的请求全部失败，没人补发。
3. 出了故障无法回答"这条通知到底发出去没有"。

**项目目标：** 把"不可靠的一次 HTTP 请求"，变成"有记录、可追踪、可重试的一次事件投递"。

**要解决的问题：** 直连 HTTP 是尽力而为，没有人为结果负责。本项目就是站在中间负责这件事的组件——收下、记住、反复送，直到送达或明确失败。

## 二、用户与痛点

**目标用户：没有运维能力、却需要可靠事件通知的个人开发者和小团队。**

他们的处境是：

- 要接收第三方平台的 Webhook（支付、表单、代码托管、消息平台），再转发到自己的业务服务；
- 自己搭 Kafka / RabbitMQ 太重，运维成本高于收益；
- 但又不能接受"通知丢了没人知道"，需要能查、能重试、能确认结果。

### 一个具体的场景

你的应用接了支付平台的回调：支付成功后，平台 POST 一条通知到你的 `/notify`，你据此更新订单状态。

某天你的服务重启了 30 秒。这 30 秒里有 12 条通知全部失败——支付平台大多只重试有限次，甚至根本不重试。结果这 12 笔订单永远停在"未支付"，而用户实际已经付过钱了。更麻烦的是事后无从查证：到底是平台没发，还是你没收到？

这就是现状的缩影：**通知在传输环节丢失，而且没有任何一方为它负责。**

### 现在大家是怎么应对的

| 做法 | 怎么运作 | 问题在哪 |
|---|---|---|
| **1. 发完就不管** | 业务代码里直接发一次 HTTP 请求，失败就打条日志 | 失败即丢失；没有记录，事后无法追溯；下游重启期间的请求全部作废 |
| **2. 自己写重试逻辑** | 在业务代码里加循环重试，或者写个定时任务扫数据库补发 | 能解决一部分，但**每个系统都要重写一遍**；重试间隔、次数上限、超时判定这些细节极易写错；补发逻辑和业务逻辑纠缠在一起，越写越乱 |
| **3. 引入消息队列** | 用 Kafka / RabbitMQ 做缓冲，由队列保证重试 | 可靠性解决了，但要额外部署和运维；为了几条通知上一整套 MQ，运维成本高于收益 |
| **4. 用云厂商事件总线或商业 SaaS** | 交给 EventBridge、Hookdeck、Svix 云版这类托管服务 | 省事，但有厂商绑定和持续费用，数据在别人手里；而且学不到底层机制 |
| **5. 自建开源网关** | 部署 Convoy 这类开源方案 | 功能齐全，但要同时跑起 Postgres、Redis 和独立 worker，对单机小项目仍然偏重 |

**本项目的定位：填在第 2 种和第 5 种之间。**

不用在每个系统里重复写重试逻辑，也不用为了几条通知部署一整套基础设施。一个二进制文件加一个 SQLite 文件，就能拿到"不丢、可查、能重试"这三项保证。

一句话概括这个缺口：**需求是消息队列级别的可靠性，手上的资源却只够跑一个单进程程序。**

### 同类项目调研

这个需求市场上确实已经有人解决过，我调研到的主要参照物：

| 项目 | 形态 | 与本项目关系 |
|---|---|---|
| **Convoy** | 开源，Go 编写、用 chi 做路由；依赖 Postgres + Redis，用 Asynq 做队列；Elastic License 2.0（源码可见但非严格开源） | 功能与本项目高度重叠，技术栈也最接近，是最直接的参照物 |
| **Svix** | 开源服务端（MIT），Rust 编写，功能最完整 | 重试策略是公开的，可作为本项目参数取值的依据 |
| **Hookdeck Outpost** | Apache 2.0，可自托管 | 另一个开源实现参照 |
| 云厂商事件总线（EventBridge 等） | 商业服务 | 有厂商绑定与费用 |

**结论：本项目不做"更好的产品"，做的是复现并理解它的核心机制。**

差异在规模而不在原理：Convoy 要同时跑起 Postgres、Redis 和独立的 worker 才能工作，本项目是单个二进制加一个 SQLite 文件，没有任何外部依赖。我要亲手实现的部分——队列语义、状态机、退避重试、崩溃恢复——恰好是这类项目内部的骨架，我只是把它外围的运维复杂度全部剥掉了。

对学习项目来说，"已有现成方案"不构成问题，反而是好事：有真实的参照物可以对照，能验证我的设计和参数取值是否合理。

## 三、功能需求

### 核心必做（保底交付）

| 编号 | 功能 | 具体行为 | 失败时 |
|---|---|---|---|
| F1 | 端点管理 | 创建端点，配置目标 URL，生成接收地址；可停用 | — |
| F2 | 接收事件 | `POST /hooks/{id}`，收到即写入数据库（状态 pending），立即返回 202 和事件 ID，**不等投递结果** | 端点不存在 404；端点已停用 410；body 超过 1 MB 返回 413 |
| F3 | 异步投递 | 后台 worker 从库中取 pending 事件，POST 到目标地址；每次投递都写一条 attempt 记录（状态码、耗时、错误信息） | 非 2xx、超时、网络错误均计为失败 |
| F4 | 自动重试 | 按递增间隔重试，最多 5 次，间隔 5s → 30s → 2min → 10min → 1h | 5 次用尽置为 failed 终态 |
| F5 | 查询 | 事件列表（可按状态过滤）/ 事件详情 / 该事件的全部投递历史 | — |
| F6 | 手动重试 | 把 failed 事件重置为 pending，立即重新投递 | — |

F2→F3 是主链路，任何情况下都要通；F4~F6 在主链路完成后补齐。

### 关键参数（明确取值）

上一版这里只写了"递增间隔""次数上限"，没有给数值，这是范围模糊的主要原因。现在定死：

| 参数 | 取值 | 依据 |
|---|---|---|
| 单次投递超时 | 10 秒 | 参考 Svix 的 15 秒，本项目取更保守的值 |
| 成功判定 | HTTP 2xx 且在超时内响应 | 沿用 Svix 的"仅 2xx 算成功"原则 |
| 重试次数上限 | 5 次 | Svix 为 8 次（总跨度约 42 小时），本项目压缩 |
| 重试间隔 | 5s → 30s → 2min → 10min → 1h | 参考 Svix 的递增策略简化而来 |
| payload 上限 | 1 MB | 超过返回 413 |
| 崩溃超时回收 | processing 超过 60 秒未更新即回收为 pending | 保证进程被 kill 后事件不卡死 |
| worker 数量 | 默认 1，代码支持配置 N | SQLite 是单写者 |

### 接口清单

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/endpoints` | 创建端点 |
| GET | `/api/endpoints` | 端点列表 |
| POST | `/api/endpoints/{id}/disable` | 停用端点 |
| POST | `/hooks/{id}` | 接收事件（对外暴露的接收口） |
| GET | `/api/events` | 事件列表，可按状态过滤 |
| GET | `/api/events/{id}` | 事件详情 |
| GET | `/api/events/{id}/attempts` | 该事件的投递历史 |
| POST | `/api/events/{id}/retry` | 手动重试 |
| GET | `/healthz` | 健康检查 |

### 状态流转

```
pending → processing → delivered
             │
          失败 ↓         ↑ 退避到期
          retrying ──────┘
             │
        次数耗尽 ↓
           failed ──手动重试──→ pending
```

### 拓展加分（时间充裕再做）

- 签名验证（HMAC），确认事件来源可信
- 请求 ID 全链路追踪，结构化日志可直接检索
- 优雅退出：收到终止信号时完成在途投递再退出
- 完整的测试覆盖与性能基准
- Docker 镜像与 CI

## 四、非功能需求

**运行环境**

- 开发：Windows 11 + Go 1.27。
- 部署：编译成单个二进制文件，配一个 SQLite 文件即可运行，**不需要外部数据库服务**。SQLite 用 `modernc.org/sqlite`，纯 Go 实现，不依赖 CGO，因此 Windows 上不用装 C 编译器。
- 也提供 Docker 镜像，一条命令启动。

**易用性**

- 单条命令启动：`webhook-gw serve --db ./data.db --port 8080`。
- 无前端，全部通过 REST API 操作，用 `curl` 即可完整验证。
- README 做到让陌生人 10 分钟内跑起来。
- 日志用 `log/slog` 结构化输出，便于排查。

**性能与可靠性**

- V0.1 以正确性为目标，**不设高并发指标**，不做性能基准。
- 并发投递的 worker 数默认 1（SQLite 是单写者），但代码按可配置 N 个的结构写，为后续留出空间。
- 事件从接收到首次投递的延迟在秒级；进程重启后，在途任务的扫描在 1 秒内恢复。
- 采用"至少一次"投递语义：**保证不丢，不保证不重复**，重复由接收方幂等处理。
- 数据量定位在单机千级事件，不做分库分表。

## 五、项目边界

**明确不实现：**

- 用户注册登录、权限系统、多租户
- 前端页面
- 消息队列中间件（Kafka / RabbitMQ）
- 分布式部署、集群
- 监控告警体系
- 签名验证（推迟到拓展阶段）

**规模控制纪律：** 17 周、每周 3~4 小时。任何"顺手加了也行"的功能一律记进 backlog，V0.1 期间不顺手加；每周结束时程序必须能跑、能演示，不留半成品跨周。

不用消息队列这条要多说一句：本项目的学习重点就是亲手实现队列语义，引入中间件等于把要练的东西外包出去。

## 六、大模型使用规划

**工具：WorkBuddy**（能直接在我的项目目录里读文件、改文件、跑 `go build`、跑测试、看 git 状态）
**模型：DeepSeek**

选这个组合的理由：WorkBuddy 让 AI 的产出可以直接在真实项目里验证，不用手动复制粘贴代码，这对长周期项目很重要；DeepSeek 中文技术交流顺畅，解释报错和标准库用法比较清楚，响应快，适合"问一句、改一处"的学习节奏。

### 分环节怎么用

| 环节 | 交给模型做什么 | 我做什么 |
|---|---|---|
| 需求梳理 | 把零散想法整理成文档结构，帮我发现遗漏（比如数据库迁移策略、`.gitignore` 这类容易漏的项） | 决定做什么、不做什么，拍板范围 |
| 系统设计 | 提供选型对比与取舍建议，指出设计缺陷（例如"channel 里装事件数据，进程崩溃时会丢任务"） | 做最终设计决策，判断建议是否成立 |
| 编码 | 脚手架、目录结构、样板 handler、建表 DDL、Dockerfile、README、CHANGELOG | 定义接口与状态流转，审读产出 |
| 调试 | 解释报错信息、讲标准库 API 的行为、枚举测试的边界条件 | 复现问题、验证修复是否真的生效 |

### 人为主导，人工校验

这是我对自己定的三条约束：

1. **关键逻辑必须自己看懂。** worker 取任务的并发逻辑、状态机流转、退避重试的边界判断这三处是项目核心，模型可以写第一版，但必须逐行讲清理由，讲不明白就重写。否则项目做完了，我的 Go 水平并没有变。
2. **产出必须跑起来才算数。** 模型给的代码不直接收，编译、运行、演示过一遍才知道对不对。验收标准写成可演示的动作，而不是"功能列表勾完"。
3. **每周做一次复盘校验。** 每周结束对照当周目标检查模型产出，并把"做成了什么 / 卡在哪 / 下周怎么调"三行写进 `docs/08-retrospective.md`。

我后端基础还不深，所以这个过程本身也是学习过程：不追求一次写对，追求每一处改动我都能说出为什么。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 范围膨胀 | 时间被稀释，做不完 | 严守第五节的边界，新想法一律进 backlog，不顺手加 |
| 时间不足 | 里程碑顺延 | 先做核心，砍单顺序已排好：先砍测试规模，再砍 API 的过滤分页，最后才降级崩溃恢复。**主链路和设计文档绝不砍** |
| Go 并发踩坑（goroutine 泄漏、竞态） | 卡壳耗时 | 回到小例子单独验证；用 `go vet` 和 `go test -race` 检查 |
| 对模型输出缺乏判断力 | 收到能跑但不对的代码 | 第六条那三条约束；关键逻辑要求逐行解释 |
| 至少一次投递带来的重复 | 被误认为 bug | 文档中明确语义，说明由接收方做幂等 |

时间风险是真实存在的：预算是 55~70 小时，含测试与文档的完整估算约 75~110 小时，缺口 20%~40%。我已经据此主动砍掉了约 20% 的范围（去掉 `cobra`、`viper` 和 CLI 双入口），把省下的时间投到"能讲清每一处设计取舍"上。

**总体策略就一条：优先完成核心功能。** 宁可少做一个功能，也不要留下跑不起来的半成品。

## 八、预期成果

**可运行程序**

- 单二进制可执行文件 + SQLite 存储，一条命令启动；附 Docker 镜像。
- 四条可当场演示的链路：
  1. 创建端点 → 发一条事件 → 自动投递成功；
  2. 目标服务关机 → 发事件 → 自动重试 → 目标开机后送达；
  3. 重试次数耗尽变 failed → 手动重试 → 变成 delivered；
  4. 投递过程中 kill 进程 → 重启 → 事件继续投完，不丢也不卡。

**代码仓库**

- GitHub 仓库，采用 Conventional Commits 规范提交，每个里程碑打一个 tag，最终发布 `v0.1.0`。

**项目文档**

- 设计文档：项目总纲、业务说明、流程图、功能边界、数据模型、API 设计
- 工程文档：Git 工作流、README、CHANGELOG
- 过程文档：17 周每周复盘（只追加，本身就是最终复盘报告的素材）

**测试**

- 覆盖状态机流转的核心测试，通过 `go test -race`。

**最终验收**

- 能对着文档向别人讲清楚每一处设计取舍——这是我自己定的最后一条标准，也是"学了一堆技术但讲不出为什么"这种结果的唯一解药。

## 九、补充：别人会怎么评价这个项目

老师提的第二个问题：如果有人真的拿去用，他会从哪些方面判断这个项目行不行。

答案是**按下面这个顺序试**，前四步决定"能不能用"，后三步决定"敢不敢用"：

| 顺序 | 他会做什么 | 我的达标标准 |
|---|---|---|
| 1 先跑起来 | 照 README 操作 | 一条命令启动，10 分钟内跑通，不需要装任何数据库 |
| 2 试主链路 | 建一个端点，发一条事件 | 立刻拿到 202，几秒内目标收到，状态变 delivered |
| 3 故意搞坏它 | 关掉目标服务再发；投递过程中 kill 进程 | 关目标：自动重试，开机后送达；kill：重启后接着投完，不丢也不卡 |
| 4 查问题 | 找一个失败事件，想搞清楚为什么失败 | 能查到每一次投递的状态码、耗时和错误信息 |
| 5 看代码 | 打开仓库，判断能不能接手 | 状态机测试通过，`go test -race` 无告警，关键逻辑有说明 |
| 6 对照文档 | 拿着设计文档核对代码 | 文档写的状态、字段、接口与实际实现一致 |
| 7 对比同类 | 问"我为什么不用 Convoy 或 Svix" | 能说清少了什么、换来什么：零外部依赖、单文件、可完全读懂 |

这也是我把验收标准全部写成"可演示的动作"，而不是"功能列表勾完"的原因——列表勾完不代表经得起上面这七步。

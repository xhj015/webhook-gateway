# Webhook Gateway —— 功能边界与 Backlog（V0.1）

> 文档编号：docs/03-scope.md
> 定位：回答"V0.1 做到哪、不做到哪"。V0.1 期间任何"顺手加了也行"的想法，一律记到这里，不顺手加。
> 范围决策的源头见 `docs/01-business.md` 第五节。

---

## 一、V0.1 范围（已定，不再扩大）

一句话：**接收 → 落库 → 异步投递 → 自动重试 → 查询与手动重试**，五个环节构成一个闭环。

| 环节 | 已交付能力 |
|---|---|
| 接收 | `POST /hooks/{id}`，边界校验 404 / 410 / 413，先落库再回 202（带 `event_id`） |
| 落库 | 三张表（endpoints / events / attempts），SQLite + WAL，`user_version` 迁移 |
| 投递 | 后台 worker 原子抢占 + 10 秒超时投递，透传 payload 与请求头，附加两个 X-Webhook 头 |
| 重试 | 递增退避 5s→30s→2min→10min→1h，最多 5 次，耗尽转 `failed` |
| 查询 / 手动重试 | 端点列表与停用、事件列表 / 详情 / 投递历史、failed 一键重试 |
| 健壮性 | 租约回收（60s）、至少一次语义、崩溃重启不丢不卡、优雅退出 |
| 工程化 | 单元测试（含 `-race`）、Dockerfile、README、结构化日志 |

## 二、明确不做（V0.1 红线）

| 不做 | 原因 |
|---|---|
| 端点删除 | 删了它名下的事件怎么办没想清楚，V0.1 只提供停用 |
| 事件内容重放 / 编辑 | 网关是透明管道，不允许改 payload |
| 消息队列中间件（Kafka/RabbitMQ） | 亲手实现队列语义是学习目标，引入中间件等于把要练的东西外包 |
| 前端页面 | 全部通过 REST API + `curl` 操作 |
| 用户注册登录 / 权限 / 多租户 | 单实例单用户，不引入 `tenant_id` |

## 三、Backlog（按优先级排序）

> 每一条都标注了"为什么现在不做"，以及触发它进入下个版本的条件。

### 高优先级（V0.2 候选）

| 项 | 说明 | 现在不做的原因 |
|---|---|---|
| 签名验证（HMAC） | 投递时对 payload 签名，目标方验签防伪造 | 接收侧边界已预留（透传 payload），V0.1 无多用户场景，伪造风险低 |
| 指数退避 + 抖动 | 用指数曲线代替固定递增，加随机抖动防惊群 | V0.1 固定递增已满足学习目标；指数退避引入随机性后更难讲清 |
| 错误分类细化 | 区分 4xx（不重试）与 5xx / 网络错误（重试） | V0.1 简化模型：除 2xx 外一律失败重试，逻辑更统一 |
| 端点删除 | 级联处理名下事件（转 failed？归档？） | 删除语义涉及历史数据归属，需单独想清楚 |

### 中优先级

| 项 | 说明 | 现在不做的原因 |
|---|---|---|
| worker 池真正开 N | 多个 worker 并发抢占 | SQLite 单写者，V0.1 并发 1 最稳；代码已按 N 的结构写 |
| 事件列表高级过滤 / 分页 | 按端点、时间范围过滤，游标分页 | V0.1 只做按状态过滤 + limit/offset，够用 |
| 事件保留策略（retention） | 定期清理老事件 / 老 attempt | V0.1 数据量小，不做清理反而便于审计 |
| 配置管理（viper / 配置文件） | 多来源配置、优先级 | V0.1 只有 3 个 flag 参数，标准库 `flag` 足够 |
| 结构化日志落盘 / 分级 | 日志写文件、按级别路由 | V0.1 打到 stdout，由部署环境统一收集 |

### 低优先级 / 可选

| 项 | 说明 |
|---|---|
| 前端管理界面 | V0.4 平台化阶段再考虑 |
| 多租户、权限系统 | V0.4+ |
| 可观测性（指标 / 告警 / 追踪） | 需要时引入 Prometheus + OpenTelemetry |
| 性能基准 | V0.3 工程化阶段，有真实负载再测 |
| 单测覆盖率指标 | 项目书明确：M7 只写 4 个状态机测试，不设覆盖率目标 |

## 四、纪律条款

1. **V0.1 期间，上面任何一条都不做。** 想到了就写进这里，而不是写进代码。
2. 如果某个 backlog 项反复被"想要"，说明它可能比预想的更优先——在 `08-retrospective.md` 里记录，等版本收口时统一决策。
3. 范围变更的唯一入口是更新本文档 + `docs/00-project-charter.md` 的版本路线，不接受"随手改一下"。

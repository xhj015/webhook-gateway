# Webhook Gateway 项目书评审与执行计划

> 配套文档：docs/00-project-charter.md（你已有的项目书）
> 本文档定位：评审意见 + 可每周勾选的执行计划。结论先行——框架好，但预算与范围不匹配，且缺了 Git 和"发布"两个环节。

---

## 一、总体判断

**三处做得对，值得保留：**

1. 范围收敛，并且写了明确的"不做"清单和纪律条款（"顺手加了也行的一律记 backlog"）。这是绝大多数学生项目最缺的东西。
2. 技术选型避坑到位。`modernc.org/sqlite` 绕开了 CGO，Windows 上不用装 gcc——这个坑避得漂亮；`log/slog`、`net/http` 标准库优先的思路也对。
3. 验收标准写成"可演示的动作"而不是"功能列表"，并且明确"在真实终端里演示流程走通，而不是代码写完应该没问题"。这个标准定得很正。

**一个核心矛盾：预算装不下范围。**

- 一个覆盖接收→落库→投递→重试→查询→崩溃恢复的 Go 服务，含测试约 1500~2500 行。
- 熟手 30~40 小时；Go 新手同时还要学语言、工具链、并发调试，约 60~90 小时。
- 加上 5 份设计文档与收尾发布，总计约 75~110 小时。
- 你的预算是 55~70 小时（17 周 × 3.5h）。**缺口 20%~40%。**

所以真正的问题不是"能不能做完"，而是"做到几分算成功"。建议：**主动砍掉约 20% 范围**，把省下的时间投到"能讲清每一处设计取舍"上——那才是这个项目真正的产出物。

## 二、五个必须补的缺口

### 1. Git 完全缺席（最要紧）

你把"学会 git"列为核心目标之一，但项目书从里程碑到验收清单，0 处提到 git。这是最大的结构性缺口。补 `docs/06-git-workflow.md`，并在全周期执行以下纪律：

- **第 0 周（开学前，约 2 小时）**：装 git、配置 `user.name`/`user.email`、生成 SSH key、在 GitHub 建仓库、`git init` + 首次提交 + `git push`。
- **提交规范**：Conventional Commits（`feat:` / `fix:` / `docs:` / `test:` / `chore:`），一次提交只做一件事。这会让你的历史记录自己变成一份变更日志。
- **分支策略**（单人项目别演多人戏）：主干开发 + 每个里程碑打一个 tag（`m1-go-boot`、`m2-receive`…）+ 一个 `spike/xxx` 实验分支用来试错，练一次合并和一次丢弃分支。
- **第 17 周**：打 `v0.1.0` tag、发布 GitHub Release、写 `CHANGELOG.md`。
- **加分项**：故意制造一次真实失误然后用 `git revert` 回滚。亲手走一遍这个流程，比背 20 个命令管用得多。

### 2. "发布"没有被仪式化

你的目标是"从策划到终版出版"。M8 除了 Dockerfile / README / 复盘，还应明确产出：`v0.1.0` tag、GitHub Release、`CHANGELOG.md`、一次完整 demo（包含失败链路和崩溃恢复两条演示）。

### 3. 数据库迁移策略没写

表结构一旦要改，新手容易直接删库重来，数据就没了。最简方案（约 20 行）：`//go:embed schema.sql` + 启动时执行 + 用 `PRAGMA user_version` 记录版本号做条件升级。**不要引入 goose / golang-migrate**，V0.1 用不上。

### 4. 缺 `.gitignore`

Windows + Go 的最小集：`*.exe`、`bin/`、`*.db`、`*.db-journal`、`.env`。第 0 周就做，否则第一个 commit 就会把 SQLite 数据库文件提交进去。

### 5. 缺每周复盘的载体

建 `docs/08-retrospective.md`，每周只填 3 行：**做成了什么 / 卡在哪 / 下周怎么调**。17 周攒下来就是一份真实可信的复盘报告，比第 17 周硬憋出来强得多。

## 三、技术选型：砍三个，留一个

**砍掉：**

- **`viper`** → V0.1 用 `flag` + `os.Getenv` 即可，约 20 行。viper 的配置优先级解析和类型断言是典型新手坑，对这个项目收益为负。
- **`cobra`** → 只有 `serve` 一个主命令时它是纯负担（会强迫你搭一套 command 包结构）。等真的需要 `serve` / `migrate` / `replay` 三个命令时再引。
- **CLI 双入口** → 降级为 `webhook-gw serve --db ./data.db --port 8080`，或者干脆 flag。这一刀省 6~8 小时。

**保留：**

- **`chi` 值得留**。20 分钟学完，`middleware` 包顺手能学到中间件概念，比 `http.ServeMux` 写通配符舒服。
- `modernc.org/sqlite` 和 `log/slog` 选得对，不动。

## 四、一个决定成败的设计决策（建议第 1~2 周就定下来）

项目书写的是"内存 channel + 数据库轮询兜底"。这里藏着一个新手最常踩的坑：**如果 channel 里装的是事件本身，进程崩溃时 channel 里的任务就没了**——这直接违背"事件 100% 落库不丢"的目标。

正确形态是让 **数据库成为唯一真相来源**：

- 接收时先 `INSERT`（`status=pending`、`next_attempt_at=now`），**事务提交之后**再往 channel 发一个信号。
- **channel 只做唤醒，不搬运数据**：类型就是 `chan struct{}`，容量 1，非阻塞发送（满了就丢，因为数据在 DB 里）。
- Worker 取任务**不看 channel 的内容**，一律从数据库捞：`WHERE status='pending' AND next_attempt_at <= now ORDER BY next_attempt_at LIMIT 1`。
- **崩溃恢复因此天然成立**：重启后 channel 是空的，但只要启动时触发一次信号、或每秒 tick 一下，worker 就会把 pending 和超时的 processing 事件捡回来继续投。

这个设计让 **M3（队列语义）和 M6（崩溃恢复）变成同一个机制的两个侧面**，能省掉一整段返工。强烈建议写进 `docs/04-data-model.md`。

**两个配套细节：**

- **原子抢占**：用 `UPDATE ... SET status='processing', locked_until=? WHERE id=? AND status='pending'`，然后判断 `RowsAffected()==1` 来确认是否抢到。比"先查再改"安全，从根上避免竞态。
- **Worker 数量**：SQLite 是单写者，V0.1 并发数设为 1 最稳；但**代码按 N 个 worker 的结构写**（配置化，默认 1）。这样并发结构练到了，写冲突风险绕开了。worker 池留到 V0.3 再真正开。

## 五、每周 3.5 小时怎么切

一次性写 3 小时的效率，远低于分成四次。原因是每次都要重新加载上下文，而上下文切换才是新手真正的时间黑洞。建议固定成这个形状：

| 时段 | 时长 | 做什么 |
|---|---|---|
| 对齐 | 15 min | 读上周复盘，写一句"本周结束时我能演示 ___" |
| 编码 | 2 h | 只推进一个功能点，不做顺手的事 |
| 提交 | 30 min | `git commit` + 更新设计文档或 README + 必要时打 tag |
| 复盘 | 30 min | 往 `08-retrospective.md` 写 3 行 |

**铁律：每周结束程序必须可运行、可演示。** 宁可少做一个功能，也不要留下跑不起来的半成品跨周。半成品堆积是这类项目最大的死因。

## 六、17 周排期（重排版）

核心调整三点：

1. **M0 从 2 周全量设计，压到 1.5 周、只写 3 份文档**。业务、流程、数据模型必须先行；**API 文档推迟到 W5 动手前再写**——它依赖路由与请求体的最终形态，动手时写反而更准。这不违背"设计先行"，而是把设计先行的对象限定在"需求边界与数据模型"上。
2. **M1 给足时间**。Go 从零到"能写出跑得起来的服务"是陡坡，不能压缩。
3. **W17 只做发布与缓冲，不写新代码**，它本身就是溢出缓冲。

| 周次 | 里程碑 | 本周结束能在终端演示什么 |
|---|---|---|
| 0（开学前） | 环境与 Git | `git push` 成功，GitHub 上能看到仓库 |
| 1~2 | M0 设计（3 份） | 讲清"一条事件的一生"，画出状态机与三张表 |
| 3~4 | M1 Go 起步 | 垂直切片跑通：`POST /hooks/{id}` → SQLite → 202 |
| 5~6 | M2 接收链路 | 404 / 410 / 413 三个边界校验逐条演示 |
| 7~8 | M3 投递链路 | 异步投递成功，Attempt 记录落库 |
| 9~10 | M4 自动重试 | 目标关机发事件 → 自动重试 → 目标开机后送达 |
| 11~12 | M5 查询与手动重试 | failed → 手动重试 → delivered 全链路 |
| 13 | M6 崩溃恢复 | 投递中 kill 进程 → 重启 → 事件继续投递 |
| 14 | M7 测试 | 4 个状态机测试通过（`go test -race`） |
| 15 | M8 工程化 | `docker run` 一条命令跑起来 |
| 16 | 文档收口 | 陌生人照 README 10 分钟跑起来 |
| 17 | 发布与复盘 | `v0.1.0` tag + Release + CHANGELOG + demo + 复盘 |

与原计划相比的取舍：M7 从 2 周收到 1 周（只写 4 个状态机测试，**不设覆盖率目标**）；M8 从 1 周扩到 2 周（工程化 + 文档收口分开，避免最后一周堆太多）。

**如果期末落后，按这个顺序砍**：M7 测试规模 → API 的过滤/分页 → M8 的优雅退出 → M6 降级为"重启后手动触发一次扫描"。**绝不砍 M2~M5 主链路，绝不砍设计文档。**

## 七、vibe coding 的正确位置

这个项目是"硬核"项目：并发、状态机、可靠性。vibe coding 在这里是辅助，不是主导。

**交给 AI 做：**
- 脚手架、目录结构、样板 handler 骨架
- 建表 DDL、Dockerfile、README、CHANGELOG
- 解释报错、解释标准库 API 的用法
- 枚举测试用例的边界条件

**必须自己写：**
- worker 取任务的并发逻辑（第四节那个设计）
- 状态机流转（pending → processing → delivered / retrying / failed）
- 退避重试的边界判断与超时回收

这三处是这个项目的学习靶心，让 AI 代写等于把项目做废了。

**最有效的用法**：写完一个模块后，让 AI 扮演 code reviewer，只做一件事——问你 3 个"为什么这里这样写"。答得上来才算过。这比让它替你写多学 10 倍。

最后提醒一句：你的验收清单最后一条是"能对着文档向别人讲清楚每一处设计取舍"。AI 帮你写完的代码，你必须能不看代码讲出每一行的理由，否则那条验收永远勾不上。
